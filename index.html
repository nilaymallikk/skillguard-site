01 / How it reads

Same input, same report.

One scan is one pass over a folder: parse, analyze, dedupe, score, print. Nothing is decided by a model unless you invite one in, and the analysis is ordinary code you can read.

  1. Resolve

    A folder, one .md, a zip, or a git URL. Size caps and zip-traversal checks land before a byte is read.

    resolve_input

  2. Parse

    Every file walked and classified: Python into an AST, config into JSON or YAML, markdown as text.

    build_context

  3. Analyze

    Twelve analyzers read the same context and append to one findings list. None of them can delete a finding.

    static_runner to 12 analyzers

  4. Merge

    Two analyzers, one problem: the finding merges with both locations instead of counting twice.

    deduplicate

  5. Forget what you accepted

    Anything in your baseline never reaches the score, so later scans report only what is new.

    apply_baseline

  6. Score

    Severity points, times 1.3 if the skill ships executable scripts, capped at 100.

    score

  7. Print

    Terminal, JSON, Markdown or SARIF. The JSON shape is the contract other tools build on.

    report

What the twelve look for

  • Prompt injection
  • Anti-refusal
  • Data exfiltration
  • Privilege escalation
  • Dangerous execution (AST)
  • Supply chain patterns
  • Dependencies
  • Shipped files
  • Known CVEs --osv
  • MCP config
  • MCP least privilege
  • MCP tool poisoning

The Python analysis is behavioral, because indirection is the whole trick: getattr(os, "system") trips the same rule as os.system.

03 / The score

Arithmetic, not a vibe.

A model never touches this. Add the points, apply the multiplier, clamp, read the band. Every score is reproducible by hand.

Points per finding

CRITICAL50
HIGH25
MEDIUM10
LOW5

Baselined findings are dropped before the sum, not scored and hidden, so accepting one is a real decision.

The multiplier

Everything weighs 30% more when the skill ships scripts that can execute:

.py .sh .bash .zsh .js .mjs .cjs .ts .rb .pl .ps1 .bat

Worked example

  • 1 CRITICAL + 1 HIGH50 + 25 = 75
  • ships a .py script75 x 1.3 = 97
  • band 81 to 100CRITICAL, DO_NOT_INSTALL, exit 1

Bands, and what CI should do about them

ScoreSeverityRecommendationExit
0 to 20LOWSAFE0
21 to 50MEDIUMCAUTION0

Exit 2 means the scan itself failed. A crash and a hostile skill are different results, and your pipeline should be able to tell them apart.

04 / Ship it

Make the score a gate.

Scan the repo on every push, and fail the build when the score crosses 50. The finding shows up in the pull request as a code scanning alert, next to the line that caused it.

.github/workflows/scan-skill.yml 
- uses: astral-sh/setup-uv@v5
- run: uv sync --all-extras

# SARIF first, so alerts exist even when the gate fails the build
- run: uv run skillguard scan . --format sarif -o skillguard.sarif
  continue-on-error: true
- uses: github/codeql-action/upload-sarif@v3
  with: { sarif_file: skillguard.sarif }

# the gate: exits 1 above 50
- run: uv run skillguard scan .

Reports come out as terminal, json, markdown or sarif. Add --fail-on-findings to fail on any finding at all. The complete workflow lives in docs/examples/scan-skill.yml.

Scan the next skill you were about to install. If it comes back clean you lost thirty seconds. If it does not, you just avoided a very bad afternoon, and you have the line number to prove it.
