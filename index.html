01 · How it reads

Same input, same report. Every time.

One scan is one pass over a folder: parse, analyze, dedupe, score, print. No model decides anything unless you invite one in, and the analysis is ordinary code you can read.

  1. 1

    Resolve

    A folder, one .md, a zip or a git URL. Size caps and zip-traversal checks land before a single byte is read.

    resolve_input
  2. 2

    Parse

    Every file walked and classified: Python into an AST, config into JSON or YAML, markdown as text.

    build_context
  3. 3

    Analyze

    Twelve analyzers over the same context, all appending to one findings list. None of them can delete a finding.

    static_runner → 12 analyzers
  4. 4

    Merge

    Two analyzers, one problem: the finding is merged with both locations, not counted twice.

    deduplicate
  5. 5

    Forget what you accepted

    Anything already in your baseline never reaches the score. Later scans report only what is new.

    apply_baseline
  6. 6

    Score

    Severity points, times 1.3 if the skill ships executable scripts, capped at 100.

    score
  7. 7

    Print

    Terminal, JSON, Markdown or SARIF. The JSON shape is the contract other tooling builds on.

    report

What the twelve look for

  • Prompt injection
  • Anti-refusal
  • Data exfiltration
  • Privilege escalation
  • Dangerous execution (AST)
  • Supply chain patterns
  • Dependencies
  • Shipped files
  • Known CVEs --osv
  • MCP config
  • MCP least privilege
  • MCP tool poisoning

The Python analysis is behavioral, because indirection is the whole trick: getattr(os, "system") trips the same rule as os.system.

03 · The score

Arithmetic, not a vibe.

A model never touches this. Add the points, apply the multiplier, clamp, read the band. You can reproduce any score on paper.

Points per finding

CRITICAL50
HIGH25
MEDIUM10
LOW5

Findings you baselined are dropped before the sum, not scored and hidden, so accepting one is a real decision rather than a cosmetic one.

Then the multiplier

score = min(100, Σ points × 1.3)

Everything weighs 30% more when the skill ships scripts that can actually execute: .py .sh .bash .zsh .js .mjs .cjs .ts .rb .pl .ps1 .bat.

Bands, and what CI should do about them

ScoreSeverityRecommendationExit
≤ 20LOWSAFE0
21 to 50MEDIUMCAUTION0
51 to 80HIGHDO_NOT_INSTALL1
81 to 100CRITICALDO_NOT_INSTALL1

Exit 2 means the scan itself failed. A crash and a hostile skill are different results, and your pipeline should be able to tell them apart.

04 · Ship it

Make the score a gate.

Two commands end the argument: scan the repo on every push, and fail the build when the score crosses 50.

.github/workflows/scan-skill.yml 
- uses: astral-sh/setup-uv@v5
- run: uv sync --all-extras

# SARIF first, so alerts exist even when the gate fails the build
- run: uv run skillguard scan . --format sarif -o skillguard.sarif
  continue-on-error: true
- uses: github/codeql-action/upload-sarif@v3
  with: { sarif_file: skillguard.sarif }

# the gate: exits 1 above 50
- run: uv run skillguard scan .

Reports come out as terminal, json, markdown or sarif. Add --fail-on-findings if you would rather fail on any finding at all. The complete workflow lives in docs/examples/scan-skill.yml.

Scan the next skill you were about to install. If it comes back clean, you lost thirty seconds. If it does not, you just avoided a very bad afternoon, and you have the exact line number to prove it.
